## **Purpose**

This folder contains the **canonical templates** used by the PaintFactor DevOS and SpecFactory systems to generate **deterministic, reviewable, database-ready specifications**.

These templates define the **structure and contract** for all spec artifacts generated during development.

They are **not runtime artifacts** for the PaintFactor application.
 They are **development artifacts** used to:

* design and validate specs

* standardize domain knowledge

* support schema design

* seed databases later

* enable human review and governance

---

## **Design Philosophy**

PaintFactor is designed to be:

* **Database- and function-driven**

* **Deterministic by default**

* **Explainable to humans**

* **Auditable and versioned**

* **Resistant to "AI hallucination creep"**

These templates enforce that philosophy by ensuring:

* structure is fixed before content is generated

* assumptions and risks are explicit

* quality tiers are modeled through logic, not prose

* every artifact has a version and review state

* AI outputs are *drafts*, not truth

---

## **Folder Structure**

Each spec family generated by SpecFactory will live in:

`specs/<spec_family_id>_v<major>/`

Using the following files:

| File | Purpose |
| ----- | ----- |
| `spec.json` | Defines the spec family, configuration dimensions, paintable items, variants, and PaintScope input mappings |
| `materials.json` | Defines material systems, coverage profiles, and consumables with yield models |
| `sop_modules.json` | Defines modular SOP blocks with nested tasks, phase assignments, and quality notes |
| `production.json` | Defines production rates per task, factor modifiers, and quality tier effects |
| `research.json` | Records domain research, PaintScope key requirements, and agent guidance |
| `qa_report.json` | Records Critic validation results with structured gates (pass/fail/warnings) |
| `CHANGELOG.md` | Human-readable history of changes |
| `human_feedback/` | Directory containing human feedback gate files |

The files in `_templates/` define the **required structure** for each of these artifacts.
The files in `_schemas/` define the **JSON Schema** for validation.

## **Key Structural Elements (Updated 2026-01)**

### **PaintScope Integration**

All specs must declare their required PaintScope inputs:

```json
"required_paintscope_inputs": [
  {
    "input_name": "IN_SF_WALL_FIELD",
    "paintscope_key": "PS_SURFACE_SF.WALL_FIELD",
    "uom": "SF",
    "required": true,
    "description": "Total paintable wall surface area"
  }
]
```

### **SOP Module Structure**

Modules now contain nested tasks with full metadata:

```json
{
  "module_id": "SOP_PREP_DRYWALL",
  "name": "New Drywall Prep",
  "description": "Prepare surfaces for primer",
  "phase": "prep",
  "applies_when": {},
  "required_inputs": [...],
  "tasks": [
    {
      "task_id": "TASK_INSPECT",
      "name": "Inspect Surface",
      "description": "Walk surfaces checking for defects",
      "skill_level": "journeyman",
      "tools_required": ["work light"],
      "quality_notes": {
        "QT2": "Major defects only",
        "QT3": "Major and moderate defects",
        "QT4": "Comprehensive inspection"
      }
    }
  ]
}
```

### **Production Rate Structure**

Rates link to PaintScope keys and include ranges:

```json
{
  "task_id": "TASK_ROLL_WALL",
  "required_input_key": "IN_SF_WALL_FIELD",
  "paintscope_key": "PS_SURFACE_SF.WALL_FIELD",
  "unit_of_measure": "SF",
  "rate_per_hour": 400,
  "rate_range_low": 350,
  "rate_range_high": 450,
  "rate_basis_notes": "Single journeyman, 9ft walls, smooth texture"
}
```

## **Artifact Lifecycle**

All spec artifacts follow this lifecycle:

1. **Draft**

   * Generated by SpecFactory

   * Review required

   * Assumptions and uncertainty expected

2. **Reviewed**

   * Human has reviewed outputs

   * Issues resolved or accepted

3. **Approved**

   * Considered safe for database seeding

   * Used by estimating logic

   * Locked except via versioned changes

4. **Deprecated**

   * Retained for history

   * Not used in active workflows

Every artifact must include:

* `version`

* `status`

* `review_required`

* `change_log`

## **Validation Gates (Critic)**

The QA report now includes structured validation gates:

| Gate | Purpose |
| ---- | ------- |
| `schema_compliance` | All files valid against JSON schemas |
| `paintscope_readiness` | All required PaintScope keys exist in catalog |
| `uom_alignment` | Task UOMs match input UOMs |
| `edge_lf_declarations` | Edge work has corresponding EdgeLF inputs |
| `modifier_math` | Modifiers correctly apply as time multipliers |
| `spray_backroll_coupling` | Spray rate ≤ backroll rate when coupled |

## **Determinism Rule (Critical)**

PaintFactor specs must be **deterministic-first**.

That means:

* Calculations must be expressible via database logic and functions

* SOPs must be composable from modular tasks

* Quality must be modeled through:

  * additional task rounds

  * material system selection

  * explicit factors

* Not through vague prose or hidden logic

AI is used to **assist development**, not to replace deterministic execution.

---

## **Quality Tiers**

Quality tiers (QT2, QT3, QT4, QT5) are **conceptual drivers**, not arbitrary multipliers.

In specs, quality differences should be expressed via:

* different execution standards per task (`quality_notes`)

* different material systems

* time modifiers applied correctly (`effective_rate = base_rate / modifier`)

* additional SOP rounds only when truly needed

If a quality difference cannot be explained in plain language to a professional painter, it should not be encoded.

---

## **Human-in-the-Loop Requirement**

All spec artifacts are generated with:

`"review_required": true`

until explicitly reviewed and approved by a human.

The system must never silently "promote" a spec to approved.

Human judgment is mandatory for:

* production rates

* material system choices

* economic edge cases

* risk acceptance

## **Schema Alignment**

Templates in `_templates/` and schemas in `_schemas/` must stay synchronized.

| Template | Schema |
| -------- | ------ |
| `spec.json` | `spec.schema.json` |
| `materials.json` | `materials.schema.json` |
| `sop_modules.json` | `sop_modules.schema.json` |
| `production.json` | `production.schema.json` |
| `research.json` | `research.schema.json` |
| `qa_report.json` | `qa_report.schema.json` |

When updating templates, always update the corresponding schema.

---

## **Versioning & Change Discipline**

Any modification to a spec artifact requires:

* incrementing the version

* updating the changelog

* preserving prior versions

* re-running QA (Critic review)

No "silent edits."

## **Common Mistakes to Avoid**

* ❌ Embedding production rates inside SOP prose

* ❌ Mixing material selection into SOP tasks

* ❌ Using quality tiers as vague labels

* ❌ Hiding assumptions or uncertainty

* ❌ Letting AI outputs bypass human review

* ❌ Computing geometry inside specs (use PaintScope)

* ❌ Applying modifiers as rate multipliers (they're time multipliers)

* ❌ Creating edge work without declaring EdgeLF inputs
