## **Purpose**

This folder contains the **canonical templates** used by the PaintFactor DevOS and SpecFactory systems to generate **deterministic, reviewable, database-ready specifications**.

These templates define the **structure and contract** for all spec artifacts generated during development.

They are **not runtime artifacts** for the PaintFactor application.  
 They are **development artifacts** used to:

* design and validate specs

* standardize domain knowledge

* support schema design

* seed databases later

* enable human review and governance

---

## **Design Philosophy**

PaintFactor is designed to be:

* **Database- and function-driven**

* **Deterministic by default**

* **Explainable to humans**

* **Auditable and versioned**

* **Resistant to “AI hallucination creep”**

These templates enforce that philosophy by ensuring:

* structure is fixed before content is generated

* assumptions and risks are explicit

* quality tiers are modeled through logic, not prose

* every artifact has a version and review state

* AI outputs are *drafts*, not truth

---

## **Folder Structure**

Each spec family generated by SpecFactory will live in:

`specs/<spec_family_id>/`

Using the following files:

| File | Purpose |
| ----- | ----- |
| `spec.json` | Defines the spec family, configuration dimensions, paintable items, and variants |
| `materials.json` | Defines finish systems, coverage behavior, consumables, and compatibility |
| `sop_modules.json` | Defines LEGO-style SOP modules, atomic tasks, and quality rounds |
| `production.json` | Defines production rates, factors, and quality behavior |
| `qa_report.json` | Records Critic review results (pass/fail/warnings) |
| `CHANGELOG.md` | Human-readable history of changes |

The files in `_templates/` define the **required structure** for each of these artifacts.

---

## **Artifact Lifecycle**

All spec artifacts follow this lifecycle:

1. **Draft**

   * Generated by SpecFactory

   * Review required

   * Assumptions and uncertainty expected

2. **Reviewed**

   * Human has reviewed outputs

   * Issues resolved or accepted

3. **Approved**

   * Considered safe for database seeding

   * Used by estimating logic

   * Locked except via versioned changes

4. **Deprecated**

   * Retained for history

   * Not used in active workflows

Every artifact must include:

* `version`

* `status`

* `review_required`

* `change_log`

---

## **Determinism Rule (Critical)**

PaintFactor specs must be **deterministic-first**.

That means:

* Calculations must be expressible via database logic and functions

* SOPs must be composable from modular tasks

* Quality must be modeled through:

  * additional task rounds

  * material system selection

  * explicit factors

* Not through vague prose or hidden logic

AI is used to **assist development**, not to replace deterministic execution.

---

## **Quality Levels**

Quality tiers (e.g., QL-3, QL-4, QL-5) are **conceptual drivers**, not arbitrary multipliers.

In specs, quality differences should be expressed via:

* additional SOP rounds (e.g., sanding, inspection)

* different material systems

* tighter tolerances and prep

* selective multipliers only when unavoidable

If a quality difference cannot be explained in plain language to a professional painter, it should not be encoded.

---

## **Human-in-the-Loop Requirement**

All spec artifacts are generated with:

`"review_required": true`

until explicitly reviewed and approved by a human.

The system must never silently “promote” a spec to approved.

Human judgment is mandatory for:

* production rates

* material system choices

* economic edge cases

* risk acceptance

---

## **Schema Alignment**

These templates are intentionally shaped to map cleanly to a future database schema.

However:

* The templates are **not the schema**

* The schema will be derived from stable patterns across many specs

* Schema decisions are owned by the **Schema Engineer**, not the SpecFactory

If a spec artifact requires a schema change, that change must be surfaced explicitly.

---

## **Versioning & Change Discipline**

Any modification to a spec artifact requires:

* incrementing the version

* updating the changelog

* preserving prior versions

* re-running QA (Critic review)

No “silent edits.”

---

## **Common Mistakes to Avoid**

* ❌ Embedding production rates inside SOP prose

* ❌ Mixing material selection into SOP tasks

* ❌ Using quality tiers as vague labels

* ❌ Hiding assumptions or uncertainty

* ❌ Letting AI outputs bypass human review

---

## **Intended Future Use**

Once PaintFactor is implemented:

* These spec artifacts will be:

  * imported into the database

  * used by estimating and planning logic

  * referenced by UI flows

* AI features may later:

  * suggest defaults

  * flag anomalies

  * assist with revisions

But the **source of truth remains structured data**, not AI output.
